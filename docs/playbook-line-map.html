Station 1 · Start

The first prompt

Frame every new project the same way. One prompt sets the goal and the definition of done, asks for a plan before code, names the agents and makes testing and git part of the job from minute one.

Kickoff prompt · fill in the yellow parts
New project: <name>. Goal: <one sentence>.
Done when:
1. <criterion a user or player can check>
2. <criterion>
3. <criterion>
Stack and limits: <language or engine and version>. Do not add dependencies without asking.
Step 1. Read and plan only. Read the repo and any CLAUDE.md. List edge cases and risks first. Ask me up to 3 questions. Then write a plan: the files to create, the approach and the test plan. Wait for my OK before you write code.
Step 2. Set up before features. Create CLAUDE.md with the build, test, lint and type-check commands and our conventions. Set up <test framework> with one passing test.
Agents: use scout (Haiku) for searches and file reads, builder (Sonnet) for well-specified implementation from the agreed plan, and stay on Opus for design and hard debugging. Have a fresh-context reviewer check the plan.
Testing: after every change, run the tests, linter and type checker and show me the real output. Iterate until they pass before you say done. Write tests from the spec, not from the implementation.
Git: work on a feat/ branch in its own worktree, commit each step, and open a draft PR early.
At the end of each session, summarize what changed, what is open and what is blocked. If I correct you twice on the same thing, propose a CLAUDE.md rule.

Add for a Godot project 
Engine: Godot 4.7, typed GDScript everywhere. Tests use GUT; run them headless with $env:GODOT and treat exit code 0 as a pass. Parse-check every script you touch with --check-only. Gameplay feel cannot be tested headless, so end each step by telling me what to playtest and what to look for.

Give the agent a detailed prompt that states the goal, source material to read first, and constraints

Specific framing with pointers to relevant sources produces better first results on exploratory tasks.

You will see
First prompts name articles or code to read, the target outcome and what is out of bounds.

Coach watches for
  • Short prompts with no file or goal (P3 Context)
  • Big changes with no plan step (P2 Workflow)

Station 2 · Set up

Rules, agents and hooks

Make the good path the default before the first feature: short rules the agent always loads, agents for each kind of work, and hooks that enforce what rules only ask for.

Set constraints around agents (lints, tests, rules) rather than relying on prompt wording for code quality

Quality depends on the guardrails the agent works inside.

You will see
Linters, type checks and test gates run automatically on agent output.

Coach watches for
  • Setup audit cards: rules the session ignores, stale or bloated CLAUDE.md, missing hooks
3
Station 3 · Plan

Spec first, code second

Specification quality, not prompt tricks, separates strong agent users from weak ones. Plan in a separate step and re-plan when work goes sideways.

Keep human judgment on the outer loop and don't delegate decisions about goals and acceptance

Agents can finish tasks without owner judgment, and the human must set the boundary.

You will see
You define goals and approve results, while the agent iterates inside the loop.

Coach watches for
  • Big change with no plan step (P2 Workflow)
  • Two or more correction prompts (P1 Workflow)

Station 4 · Build

Delegate and run in parallel

Routine code goes to cheaper models, judgment stays on the top model, and parallel sessions each get their own worktree so nobody overwrites anybody.

No practice in today's playbook landed on this station.

Add to your setup
  • habitdelete-stale-uv-lock When getting confusing dependency errors in a library project, delete the gitignored uv.lock and re-run.
Coach watches for
  • Edits to files Claude never read (P2 Quality)
  • One file edited 5+ times (P1 Quality)
  • Long session with no subagents (P3 Tokens & cost)
5
Station 5 · Verify

Close the loop

An agent that can check its own work and iterates until the check passes produces 2 to 3 times better results. Make it prove things, and review it like a skeptic.

Plan the work, have a second agent review it, then review and test it yourself before shipping

A plan, an independent agent review and a human check keep AI-built code from being unreviewed 'vibe coding'.

You will see
Each change shows a written plan, a separate reviewer-agent pass and your own test run before the commit or PR.

Build evals from real conversation traces and check the graders themselves

Automated graders can disagree with human judgment, so they must be validated against annotated traces.

You will see
An eval set derived from real traces exists, and its grader has been compared with human labels.

Treat verification as the bottleneck and write checks that prove correctness, not just that code was produced

Writing code is now cheap, while knowing it is correct is the scarce part.

You will see
Tasks include a done-when check, such as tests or a repro, that runs before the work is accepted.

Add to your setup
  • commandbuild-eval-hill-climb The claude-api plugin's build_eval and hill-climb commands build evals, check the graders and iterate the app against them.
  • agentsecond-agent-reviewer A separate reviewer agent critiques plans and diffs before the human review.
Coach watches for
  • 5+ edits since the last test, lint or type check (P2 Quality)
  • The same command failing twice (P1 Quality)

Station 6 · Ship

Branch, PR, merge

Small, visible steps reach main through pull requests. Checks run before every merge, and a bad turn is always one revert away.

No practice in today's playbook landed on this station.

Coach watches for
  • Uncommitted changes on main (P2 Git)
  • 10+ files or 300+ lines uncommitted (P2 Git)
  • 2+ hours since the last commit with work pending (P3 Git)

Station 7 · Learn

Turn mistakes into rules

Every repeated correction is a missing rule, skill or eval. Learn feeds straight back into the next Plan.

Audit agent instruction files periodically and remove what the agent no longer needs

Stale or bloated rules waste context and can mislead the agent.

You will see
Agent files are pruned on a schedule and shrink or stay concise.

Add to your setup
  • habitagent-file-audit Review the agent instruction files regularly and cut out anything the agent no longer needs.
Coach watches for
  • Session report and score trend against your average
  • Setup audit: rules worth adding or pruning

Context & cost line

  • Start a fresh session once context reaches roughly 300-400K tokens. Long contexts burn quota faster and degrade output quality. You will see: Sessions are restarted with a short handoff summary instead of running indefinitely.
  • Turn off or limit subagents when token usage spikes. Subagent fan-out can multiply token consumption per task and drain weekly limits. You will see: Subagent use is disabled or restricted in settings and token use per task drops.
  • Measure token consumption with a usage tool such as ccusage before blaming the model. Measured numbers show whether usage or quality has really changed instead of guessing. You will see: You compare ccusage output across days before changing your workflow.
  • commandccusage A CLI that reports Claude Code token consumption so usage anomalies can be investigated.
  • habitfresh-session-at-context-threshold Restart with a handoff summary after about 300-400K tokens of context.

Safety line

  • Choose an autonomy level per task and match review depth to the risk. Not all work warrants the same level of oversight. You will see: Risky changes get step-by-step approval, while low-risk tasks run with looser permissions.
  • Run untrusted generated HTML or code in a tight sandbox. Sandbox escapes in rendered artifacts can expose private data and APIs. You will see: Generated apps run in isolated sandboxes with no access to credentials or APIs.
